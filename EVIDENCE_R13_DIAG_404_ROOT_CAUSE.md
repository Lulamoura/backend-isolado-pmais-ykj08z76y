# R13 Diag-Compensacao-Auditoria — HTTP 404 Root Cause Analysis

## Summary

The "Executar auditoria somente-leitura" button returned HTTP 404
(`{"data":{},"message":"The requested resource wasn't found.","status":404}`)
because of an HTTP method mismatch between the backend hook and the frontend
component.

## Proven Root Cause

**Backend hook** (`pocketbase/hooks/ac_diag_compensacao_auditoria.js`):

```javascript
routerAdd(
  'GET',
  '/backend/v1/integracao/ac/diag-compensacao-auditoria',
  (e) => { ... },
  $apis.requireAuth(),
)
```

The route is registered as **GET**.

**Frontend component** (`src/components/foundation/DiagCompensacaoAuditEvidenceBlock.tsx`):

```typescript
const res = await fetch(`${import.meta.env.VITE_POCKETBASE_URL}${ROUTE_PATH}`, {
  method: 'POST', // ← MISMATCH: backend expects GET
  headers: {
    'Content-Type': 'application/json',
    Authorization: pb.authStore.token || '',
  },
})
```

The frontend called **POST**.

PocketBase's Go `http.ServeMux` returns 404 for any method+path combination
that does not exactly match a registered route. Since no `POST` handler was
registered for `/backend/v1/integracao/ac/diag-compensacao-auditoria`, the
request received the standard 404 response.

## Verification — No Execution, No Side Effects

- The 404 response is generated by PocketBase's HTTP router **before** the
  hook callback body executes. The handler function was never invoked.
- No code inside the route handler ran: no authentication check, no lock
  check, no `safeFind()`, no `safeCount()`, no `$app.save()`, no
  `$app.delete()`.
- The server-side lock (`com_parametros` key `ac_diag_compensacao_audit_lock`)
  was never read or written by this attempt.
- `audit_executed: false`
- `deletion_executed: false`
- `activecampaign_calls: 0`

## Fix Applied

Changed the frontend `fetch` call from `method: 'POST'` to `method: 'GET'`
and removed the unnecessary `Content-Type: application/json` header (GET
requests have no body).

This is the minimal change that aligns the frontend with the backend's
existing route registration. No backend changes were needed.

### What Was Preserved (Untouched)

- Fixed filters (contact_identifier, email, event_id, temporal_window, origin)
- Authentication (`$apis.requireAuth()`)
- Absence of body/client parameters
- Read-only nature (no writes, no deletes)
- Single-execution lock mechanism
- Webhook hook (`ac_webhook.js`)
- R13 runner (`ac_run_round_2d2a_r13.js`)
- RBAC rules and profile permissions
- All migrations (0001–0058)
- All collections and schema
- All secrets
- All integrations
- No new route with lower protection
- No R14
